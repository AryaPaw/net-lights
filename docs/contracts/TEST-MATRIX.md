# Net Lights – обязательная матрица приемки

Версия 1.1, 2026-09-07. Нормативный документ совместно с IMPLEMENTATION-PLAN.md. Ни один обязательный тест не считается выполненным по наличию кода теста. У каждого ID должны быть результат, команда/процедура, версия сборки и ссылка на доказательства.

## Правила выполнения

- Статусы: `RUN — PASS`, `RUN — FAIL`, `NOT RUN`. Пропуск, недоступный runner, отсутствие GUI или незавершенный soak – NOT RUN, не PASS.
- Испытания самого продукта должны использовать его реальный reducer, scheduler, limiter и HTTPS-клиент. Отдельная «правильная» копия алгоритма в тестовом проекте не доказывает продукт.
- Unit/property tests работают на виртуальном времени без реального Sleep. Управляемые сетевые fixtures работают на loopback с конечными тайм-аутами. Публичные серверы не участвуют в CI.
- Случайные сценарии имеют фиксируемый seed; при ошибке сохраняется минимальный воспроизводимый trace. Случайная повторная удача не стирает первый FAIL.
- Проверять точные границы: до/на/после TTL, дедлайна, server pause, минутного/секундного лимита, смены epoch. Границы скользящих окон определены как `(t−window,t]`.
- Временная тестовая CA доверяется только изолированному тестовому клиенту через custom trust. Не менять Windows Root Store и не отключать валидацию сертификатов в production.
- При отмене/падении runner завершает только принадлежащие ему процессы/fixtures, проверяет владение PID и время запуска. Не убивать все процессы с похожим именем.
- Логи ограничены по размеру и времени. Итог – проверенный ZIP; удалять только созданную runner временную папку после успешной архивации. Сырые доказательства и первый FAIL сохранять.

| T16 | Медленные и зависшие попытки | Не более 4 physical-inflight, 2 на группу, 1 на адрес. Счетчик не уменьшается до фактического завершения операции. |
| T17 | Минимальный интервал адреса 8 с | Соблюдается и при старте, и при подтверждении, и по кнопке. При нехватке слотов работа ждет/пропускается, а не обходит ограничение. |

| T19 | Два последовательных отказа разных инфраструктур, нет успеха 4 с | Запускается один episode; корректный EpisodeStart, включение релевантных уже запущенных попыток, без дублей. |

| T21 | Confirmation без успехов | Покрывает все 7 с учетом уже выполненных релевантных попыток; максимум 7 новых вызовов, нет рекурсивных retries. |
| T22 | Несколько источников запуска confirmation | Одновременно существует максимум один episode на группу; cooldown 15 с не обходится кликами/сетевыми событиями. |
| T23 | Исчерпание 12 с episode / точка в Retry-After | Нет фиктивного полного покрытия. При отсутствии достаточных успехов – Unknown. В обычной ротации работа продолжается. |
| T24 | Одновременный полный обрыв обеих групп | Fairness; ни одна группа не голодает; Offline обеих ≤14 с после установившейся ≥30 с работы, в условиях §10 плана. Перебрать момент обрыва по всему 14-секундному циклу шагом ≤50 мс и пограничные completions. Отдельно измерить условия полного бюджета/активного cooldown без ложного обещания этой же границы. |
| T25 | Полное и частичное восстановление после Offline | Если восстановились все 7 точек и отвечают ≤500 мс: первый выход из красного ≤3 с, Online ≤5 с. Если только 1/2 точки – отдельная проверка всех позиций ротации, ≤15 с в контрольном режиме без confirmation и внешних пауз; с confirmation измерить отдельно и исключить голодание. Доставка completion → UI snapshot ≤250 мс. Перебрать фазу расписания. |
| T26 | Устойчивый Offline 72 виртуальных часа | Нет бесконечных confirm-каскадов, роста очередей/счетчиков/памяти. Ротация продолжает обнаруживать восстановление. |
| T27 | 403/429/503 с Retry-After | Reachable в момент HTTP-ответа, затем пауза. Seconds/date/прошлая дата/некорректная/огромная дата. Не сокращать корректную долгую паузу и не менять quorum. |
| T28 | Шторм событий/кликов, незавершаемый fake transport, exception в loop | Очередь и число задач ограничены. UI получает Unknown при внутреннем сбое; нет ложного сетевого Offline, бесконечного respawn или необслуженных exceptions. |

## B. Настоящий .NET HTTPS-клиент: T29–T43

Локальный сервер должен управлять TCP, TLS и заголовками независимо. Тестировать клиент продукта, не только curl. Для доверенного loopback использовать отдельную test-only фабрику с CustomRootTrust и корректной проверкой имени/срока; не протащить bypass в Release.

| ID | Сценарий | Ожидаемое поведение |
|---|---|---|
| T29 | Нормальный HTTPS HEAD 200 и 204 | Reachable, тело не читается; HTTP/1.1 exact; request/response освобождены. |
| T30 | 301/302/307/308 на чужой URL | Reachable исходного узла, ни одного обращения по Location. |
| T31 | 404/405, удален robots.txt/изменился файл | Reachable; не нужен новый конфиг, GET fallback или ожидаемая строка. |
| T32 | HTTP 403/429/500/503 и server pause | Не превращаются в транспортный failure; правильные nextAllowedAt и expiry. Сохранить число запросов на fixture. |
| T33 | TCP принимает, TLS молчит | Unreachable по тайм-ауту; успех TCP не делает цвет зеленым. |
| T34 | TLS завершен, HTTP headers зависли/идут по одному байту | Общий deadline, не новый тайм-аут на каждый байт/этап. Неполные заголовки не Reachable. |
| T35 | Plain HTTP на TLS-порту, TLS alert, обрыв handshake | Нет Reachable; структурированная причина TLS/transport; нет перехода на HTTP. |
| T36 | Self-signed/untrusted, expired, wrong host | Indeterminate; никогда accept-all сертификатов. Отдельно нормальный сертификат после ротации. |
| T37 | NXDOMAIN, DNS задержка, смена A/AAAA | Дедлайн/отмена действительно проверены. DNS управлять внутри fixture/тестовой VM, не менять DNS владельца. При pool lifetime/новой сети используется новое соединение. |
| T38 | Refused/reset TCP, исчезновение соединения из пула | Ограниченное завершение и освобождение. Если нижележащий handler делает допустимый внутренний retry, учитывать и описать наблюдаемые попытки; application retries не добавлять. |
| T39 | HTTP status 100 без финального ответа; некорректные и >32 КиБ headers | Не Reachable; конечный deadline/лимит. Неограниченные буферы запрещены. |
| T40 | HEAD с Content-Length в гигабайты и ошибочно присланным телом | Нет скачивания/буферизации тела, память ограничена, response закрыт. |
| T41 | Shutdown/epoch cancel одновременно с success/deadline | Один итог, корректный учет inflight, нет старого зеленого/необслуженной задачи. |
| T42 | IPv4-only, IPv6-only, один адрес семейства недоступен | На поддерживаемой среде проверить фактическую .NET-стратегию. Не объявлять UDP/QUIC или все IPv6 исправными по одному HTTPS/TCP. Не отключать семейство глобально. |
| T43 | Cookies/auth/proxy/redirect/HTTP3 isolation | Нет cookies, credentials, явного системного proxy, HTTP3 upgrades. Тесты не требуют изменения глобальных настроек. После многократных запросов sockets/tasks/CTS/response objects не накапливаются. |

## Покрытие и отрицательные проверки качества тестов

Помимо перечисленных сценариев, подтвердить на временном изолированном diff, что тесты обнаруживают минимум следующие дефекты: успех по одному CDN; подмена HTTPS успехом ping; Offline по четырем непроверенным направлениям; устаревший success после новой ошибки; отмена учтена как отказ; пропущен Retry-After; старт выше бюджета; застрявшая задача освобождает physical permit; отключена валидация сертификата; EnsureSuccessStatusCode превращает 404 в outage. В основной ветке эти дефекты не сохраняются.

Branch coverage ≥90% reducer/scheduler/limiter. Не повышать цифру дублированием тестов, которые просто повторяют код. Любая непокрытая рискованная ветвь из матрицы важнее формальной цифры.

## Формат acceptance ledger

В docs/ACCEPTANCE.md создать одну строку на T01–T62:

```text
ID | RUN — PASS / RUN — FAIL / NOT RUN | команда/процедура | build/commit |
дата UTC | ожидаемое/наблюдаемое | ссылка на raw evidence | причина ограничения
```

Отдельно записать CODE COMPLETE, AUTOMATED VERIFIED, USER-VISIBLE VERIFIED, AUTONOMOUS SOAK VERIFIED. OWNER ACCEPTED назначает пользователь. Общий PASS запрещен при обязательном FAIL/NOT RUN; можно честно сдать промежуточную сборку с конкретными незавершенными пунктами.

Тестовые архивы должны содержать manifest с версиями, параметрами, seed, началом/концом, счетчиками проб, максимумом inflight/частоты/очередей и SHA256 ключевых файлов. Не включать VLESS-конфиг, cookies, credentials, приватные ключи временной CA. Публичный сертификат теста допустим.
