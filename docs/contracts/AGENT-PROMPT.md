Реализуй Net Lights в корневом каталоге этого git-проекта.

Сначала полностью прочитай IMPLEMENTATION-PLAN.md и TEST-MATRIX.md. Это канонический контракт, самодостаточный и не требующий истории чата. Прочитай доступные AGENTS.md, проверь git status и сохрани существующие файлы/исследования/чужие изменения. Не выполняй git clean/reset и не удаляй untracked tests/. Зафиксируй SHA256 обоих документов в отчете; не меняй требования или пороги молча ради PASS.

Нужно небольшое Windows 11 x64 приложение на C#/.NET 10/WinForms: одна иконка в трее – круг с левой половиной провайдера, правой VPN и узким прозрачным вертикальным вырезом. Половины независимо показывают доступность двух пулов HTTPS-адресов. VPN VLESS находится на роутере пользователя. Существующую маршрутизацию принимаем как данность. Не устанавливай VPN на ПК, не меняй роутер, DNS, сетевые адаптеры, firewall, маршруты или Windows certificate store.

Критически важно: успешный ICMP или TCP НЕ заменяет HTTPS. Они разрешены лишь в ручной диагностике. Основная проверка – единый HTTPS HEAD с обычной валидацией сертификата, без редиректов/тела/cookies; конечный HTTP 200–599 подтверждает достижимость сервера. 404 не означает пропажу интернета, 429 требует паузы. Это проверка HTTPS/TCP контрольных направлений, не гарантия UDP/QUIC или исправности всех сайтов.

Семь равноправных точек на группу перечислены в плане. Обычный запуск раз в 2 секунды на группу, дедлайн запроса 2 секунды. Дополнительное подтверждение – ограниченный проход тем же HTTPS-клиентом, через тот же лимитер. Никаких цепочек протокольных fallback, автоматического скачивания новых адресов и бесконечных retries. Одна умершая точка при других работающих не меняет индикатор на красный и не требует действий владельца.

Работай по этапам из плана: модель и scheduler с виртуальным временем; настоящий HTTPS-клиент с локальными fault fixtures; WinForms UI; сквозные и длительные тесты; Release-поставка. Не начинай с красивой иконки, оставляя сеть и ошибки недоделанными. Используй минимальное число простых компонентов, один владеющий состоянием цикл, ограниченные очереди и явное освобождение ресурсов.

Обязательно выполни матрицу T01–T62 и веди docs/ACCEPTANCE.md по каждому ID. Тесты должны проверять реальный код продукта, а не отдельную копию алгоритма. Нужны проверки ложного красного/зеленого, устаревших результатов, отмены, лимитов, одновременного падения обеих групп, TCP-успеха при зависшем TLS/HTTP, сертификатов, Retry-After, восстановления после сна/смены сети/Explorer, утечек и видимого tray UI.

Сетевые нарушения воспроизводи на loopback/в VM. Не отключай интернет пользователя и не перезапускай его Explorer без отдельного действия пользователя. Не устанавливай test CA в системное хранилище. Публичные сайты не должны быть зависимостью CI. Внешний smoke ограничен обычным бюджетом и временем. 24-часовой gate автономности выполняется на локальных fixtures, а не круглосуточной нагрузкой на публичные сайты. Виртуальные 72 часа не заменяют реальные 24 часа.

Исследования в tests/network-research-2026-09-06 содержат предварительные замеры и скрипты. Их PASS не является PASS нового приложения. Там есть сохраненный неудачный тест под ограниченным токеном и успешный повтор: не скрывай FAIL и не смешивай ошибку испытательной среды с сетевым отказом. Канонические правила – только в IMPLEMENTATION-PLAN.md, затем TEST-MATRIX.md; старые README/review нужны для контекста, не как конкурирующие требования.

Не заявляй готовность без доказательств. Для каждого обязательного теста используй RUN — PASS, RUN — FAIL или NOT RUN. Укажи CODE COMPLETE, AUTOMATED VERIFIED, USER-VISIBLE VERIFIED, AUTONOMOUS SOAK VERIFIED раздельно. Если 24 часа, VM или реальная UI-проверка не выполнены, отдай честный промежуточный статус с конкретным незавершенным gate. Не помечай OWNER ACCEPTED самостоятельно. Не ослабляй deadline/лимиты/критерии, чтобы скрыть ошибку: сначала исправь реализацию, а непреодолимое противоречие опиши предметно.

Выход: работающая Release self-contained win-x64 ZIP-сборка, исходники и фиксированные зависимости, CI, USER-GUIDE/ARCHITECTURE/ACCEPTANCE/KNOWN-LIMITATIONS, ограниченные архивы доказательств с manifest, итоговый git status и точные команды запуска/повторения тестов. Не публикуй релиз, не отправляй сообщения, не включай автозапуск на машине владельца и не меняй системные настройки самостоятельно. Исследовательские и тестовые временные папки удаляй только по проверенному владению после успешной архивации; результаты и существующие файлы сохраняй.

Начни с проверки репозитория и краткого плана этапов, затем выполняй реализацию и тесты. Не останавливайся на предложении плана или на зеленом build: задача включает проверку поведения и честную приемку.
