# Net Lights instructions

## Version proposals

Only propose or change a version when the active task requests a version proposal or release. Prefer patch for small fixes such as tray behavior, copy, or CI; prefer minor for user-visible features. Propose major only when explicitly requested.

If the release version is unspecified, propose an exact number with a brief reason and wait before editing version metadata. An exact version already supplied by the user needs no repeated confirmation. Ordinary fixes, verification, and branch pushes don't require an unsolicited version decision.

## Publication and preserved work

Follow the global Git/publication policy and actual repository verification sources. Authorization persists for the same active task, action, and target unless revoked; a new message doesn't reset it. A branch push alone doesn't authorize version bumps, tags, or releases.

The existing `.cursor/skills/net-lights-ship/SKILL.md` contains project shipping context. Consult it when that workflow applies and verify version-sensitive commands/current CI against the actual files. Preserve unrelated staged/unstaged work, including pre-existing lockfile changes; don't blindly restore files after a build.

## Актуальная локальная программа

- В конце каждой работы над проектом проверяйте, что локальная программа `artifacts/publish/NetLights.exe` соответствует актуальной проверенной версии. После изменений программы и каждого выпуска обновляйте и запускайте локальную копию без отдельного напоминания пользователя. Сборка, push или публикация релиза сами по себе эту обязанность не выполняют.
- Используйте штатную транзакционную замену из `scripts/run-local.ps1` и `scripts/local-publish-transaction.ps1`. Готовый проверенный пакет CI можно переключить тем же механизмом без повторной сборки; сверяйте версии и SHA-256 с его результатами проверки. Если исполняемые файлы уже актуальны, повторная сборка и перезапуск не нужны.
- До замены штатно завершите только подтверждённую локальную копию, сохраните настройки и обе истории и проверьте восстановление копии в отдельной папке. После запуска подтвердите путь процесса, ProductVersion, готовность монитора, устойчивость процесса и сохранность прежних записей. Не объявляйте локальное обновление выполненным по одной замене файлов.
- Курсор пользователя не трогайте. Эта обязанность не разрешает автоматически менять установленную копию в `AppData\Programs`, номер версии, Git или релизы. Явный запрет пользователя на запуск или обновление имеет приоритет; при блокировке сообщайте точную причину, не оставляя старую копию незаметно.

## Проверка изменений и расследование FAIL

- Единственный вход проверки – `scripts/verify.ps1`. Перед отправкой изменений кода или тестового стенда выполняйте локальный `-Preflight`: синтаксис PowerShell, самопроверки стенда, формат, строгий Clippy и тесты без GUI. Используйте существующие `artifacts/rust-target` и `artifacts/frameprobe-target`; не запускайте случайно полную пересборку в новом `target`. `Preflight` не подтверждает UI, runtime coverage, установку или устойчивость ресурсов.
- При падении сначала определяйте, что отказало: программа, стенд, упаковка или среда. Сохраняйте исходный FAIL и проверяйте гипотезу узким воспроизведением. Не запускайте снова весь pipeline ради выяснения того же непонятного падения и не считайте повтор без изменений исправлением.
- До нового полного CI нужен подтверждённый механизм исходного FAIL и локальная отрицательная проверка, которая обнаруживает его. Один случайный зелёный повтор узкого сценария не подтверждает устранение нестабильности. Проверяйте также запуск и остановку наблюдателя, а не только удачный кадр в середине работы.
- Для отладки захвата используйте `scripts/verify.ps1 -CapturePreflight`; это только синтаксис, самопроверки протокола и Rust-стенда без окна, GPU и ввода. Перед push по-прежнему обязателен общий `-Preflight`. Десять независимых запусков захвата проверяются отдельным диагностическим режимом; он не заменяет измерение анимации или полный UI gate.
- Автоматический push в отладочную `codex/1.7.0-ci`, меняющий только разрешённые файлы захвата, должен выполнять узкую проверку стенда. Изменения приложения, зависимостей, упаковки, самого выбора проверок, main, PR и явный финальный запуск сохраняют полный pipeline. Не объявляйте узкий статус готовностью продукта.
- В DXGI разделяйте фактический начальный снимок до тестового ввода и измеряемые кадры. Сохраняйте исходные QPC, пиксели и число накопленных обновлений начального снимка отдельно; не выдавайте их за кадры анимации. После начального снимка пропуски остаются ошибкой, а отсутствие измеряемых кадров не может подтверждать плавность.
- Порядок интерактивной проверки: локальный preflight → один узкий сценарий на одноразовой CI VM → полный CI с coverage на итоговом кандидате. Не держите параллельную полную сборку для каждой итерации отладки одного UI-теста. Автоматически начавшийся лишний прогон собственной отладочной ветки можно отменить; его статус остаётся `CANCELLED`, а обязательный итоговый полный прогон сохраняется. Точные команды и границы режимов описаны в существующей процедуре `net-lights-ship`.
- Проверяйте сам наблюдатель: завершение анимации, временное владение буфером обмена, время ответа UIA, источник времени и очистку подписок. Медленный опрос не доказывает отсутствие короткого состояния. События доступности, отрисованные кадры и снимок конечного состояния являются разными уровнями доказательства.
- После исправления повторяйте затронутый сценарий. Переносите выводы о проверке только на неизменившиеся входы; связывайте результат с commit, исходниками и хешем проверенного exe. Не называйте весь продукт исправным по локальной сборке, зелёным unit-тестам или отдельному UI-сценарию. Отменённый пользователем длительный тест не возобновляйте автоматически и не подменяйте коротким `PASS` проверки утечек.

## Интерфейс и общие механизмы

- Инерцией колеса управляет `smooth_scroll` в локальном патче `gpui-pre`. Обычные контейнеры и виртуальный список используют этот движок. Не добавляйте покадровое сглаживание или возврат смещения в отдельных страницах; переход по разделам настроек является отдельным программным действием и отменяется ручной прокруткой.
- Виртуализация истории локаций обязательна. При изменении прокрутки проверяйте также тачпад, границы вложенных областей, смену периода, перетаскивание scrollbar, reduced motion и прекращение запросов кадров после остановки.
- Подтверждения действий показываются штатными уведомлениями GPUI Kit поверх окна, без изменения компоновки страницы. Повторное действие обновляет своё уведомление. Ошибки мониторинга и сохранения остаются постоянными предупреждениями и не затираются подтверждением копирования.
- Геометрия графика является общим источником для рисования, подписей, обводки и попадания курсора. Изменение высоты полосы должно обновлять все эти потребители.
- Подбирать статическую компоновку следует на development-сборке в отдельном профиле. Итоговую Release-сборку и соответствующие проверки выполняйте после согласованной серии изменений. Development-снимок не подтверждает производительность Release.
- При адаптации Argus переносите конкретный механизм из указанного коммита с атрибуцией и проверкой потребителей. Само сходство исходников или наличие UI Kit не подтверждает визуальное соответствие. Общие права, публикацию и правила чужих системных функций из его AGENTS.md не переносите.
