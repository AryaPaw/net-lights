## 1. Задача и согласованные границы

Небольшая автономная программа для Windows, работающая в трее. Одна круглая иконка, разделенная на левый и правый полукруг узким прозрачным вертикальным вырезом. Слева провайдер, справа VPN. Цвета половин независимы.

- Провайдер: HTTPS-доступность нескольких адресов провайдера.
- VPN: HTTPS-доступность нескольких зарубежных адресов.
- VPN пользователя работает на роутере, использует VLESS. На ПК VPN-клиента нет. Существующая маршрутизация принимается как заданная. Не проверять и не менять конфигурацию роутера, VPN, DNS, firewall, маршруты, сетевые адаптеры или сертификаты Windows.
- Название VPN – согласованная подпись зарубежного пула, а не доказательство того, каким маршрутом прошел пакет. Не требовать от пользователя раздельных интерфейсов или настройки туннеля на ПК.
- Пользователь хочет надежную программу без ежедневного/еженедельного обслуживания. Неисправность одного контрольного адреса должна переноситься штатно и без необходимости править конфигурацию.
- Нужен один штатный режим. Выбор трех режимов частоты в UI не делать. Параметры фиксируются в типизированной конфигурации и проверяются тестами.
- Не создавать цепочки HTTPS → HTTP → TCP → ICMP с объявлением успеха на более слабом протоколе. Дополнительная проверка – тот же HTTPS к другому адресу.
- Не нужны Electron, WebView, браузер, база данных, сервер, установщик службы, драйвер, телеметрия, облачный backend, подписка, автоматический скачиваемый список адресов или система плагинов.

## 3. Смысл измерения и VLESS

Основной сигнал – возможность получить конечные HTTP-заголовки по HTTPS/TCP с корректной штатной проверкой сертификата. Не проверяется содержимое сайта, скорость скачивания, работоспособность его backend, UDP, QUIC/HTTP3, видеосервисы или каждый адрес интернета.

ICMP, TCP и HTTPS могут давать разные результаты. Xray описывает маршрутизацию TCP/UDP; поведение ICMP через конкретный роутер/VLESS нельзя вывести из успеха HTTPS. Программа не должна считать ping доказательством работоспособности зарубежного HTTPS. Обратное тоже верно: неответивший ping не делает успешный HTTPS неудачным.

Для v1: явно HTTP/1.1 через TLS/TCP, RequestVersionExact. Это устраняет неявное изменение проверяемого транспорта из-за HTTP/3/Alt-Svc и упрощает воспроизводимость. Отдельные TCP/ICMP-пробы – только ручная диагностика, не голосуют за цвет.

### 3.1 Классификация одной пробы

| Результат | Связность | Дополнительное действие |
|---|---|---|
| Завершены TLS с валидацией и заголовки HTTP 200–599 | Reachable | сохранить статус HTTP, время |
| 301/302/307/308 | Reachable | не идти по Location |
| 404/405 | Reachable | не требовать неизменности файла/метода, не переключать протокол |
| 403/429 | Reachable сейчас | пауза дальнейшего обращения, не превращать в outage |
| 5xx | Reachable до HTTPS-узла/CDN | состояние сайта не равно состоянию интернета; уважить Retry-After |
| DNS name failure, TCP refusal/reset, транспортный тайм-аут, TLS protocol/handshake failure без HTTP | Unreachable | отказ этого направления; причина отдельно |
| Ошибка доверия/имени/срока сертификата | Indeterminate | не отключать проверку сертификата, не говорить «сервер надежно достигнут» |
| Некорректные/слишком большие заголовки, локальный resource failure | Indeterminate | протокол/монитор не дал надежных данных |
| Отмена при выходе/смене сети/устаревшей работе | Cancelled | не записывать как отказ направления |

Не вызывать EnsureSuccessStatusCode для определения связности. Не принимать только TCP connect или неполный HTTP status line за Reachable. Не скрывать ошибки TLS общим catch со значением true. Отличать trust failure от общего handshake failure по структурированным данным исключения там, где это возможно; если надежно различить нельзя – Indeterminate, не догадка по локализованной строке.

TLS-посредник, которому доверяет Windows, остается ограничением модели. Не добавлять certificate pinning на чужие сайты: ротация их сертификатов не должна ломать утилиту. Не устанавливать свой корневой сертификат.

## 6. HTTPS-клиент и жизненный цикл запросов

- Долгоживущий HttpClient + SocketsHttpHandler. Не создавать клиент на каждый запрос.
- AllowAutoRedirect=false, UseCookies=false, UseProxy=false. Последнее относится только к явному прокси Windows/окружения: приложение пользователя должно идти через существующую сеть роутера, не выбирать локальный прокси. Не менять системные настройки. Изменение этого правила – отдельное расширение конфигурации в будущем.
- Credentials=null, PreAuthenticate=false, отсутствие auth/cookies; User-Agent NetLights/<version>.
- PooledConnectionLifetime=60 с, PooledConnectionIdleTimeout=30 с, MaxConnectionsPerServer=1, MaxResponseHeadersLength=32 КиБ. Значение lifetime – параметр приложения, не требование Microsoft; покрыть тестом DNS/соединений.
- SendAsync(HEAD, ResponseHeadersRead, token). Не читать тело и не распаковывать его. Dispose request/response/CTS во всех ветках. Сертификаты проверяет платформа, без permissive callbacks в production.
- Единственный application deadline 2 с с монотонным временем и linked cancellation (shutdown + network epoch + probe deadline). HttpClient.Timeout можно сделать Infinite при реально действующем индивидуальном deadline; ConnectTimeout не должен увеличивать общий бюджет.
- Дедлайн включает DNS, соединение, TLS, все заголовки. Ожидание очереди отдельно от длительности попытки; не запустить уже просроченную работу.
- Недостаточно Task.WhenAny и забыть оставшуюся задачу. По дедлайну запрос отменить; его фактическое завершение наблюдать, ресурсы освободить. Не выдавать освободившийся physical-inflight permit, пока нижележащая операция еще жива. Остаточные операции строго ограничены общим лимитом.
- Проверить отмену при зависшем DNS на фактическом .NET/Windows. Если результат не приходит вовремя, UI получает Indeterminate/deadline, но нельзя бесконечно плодить новые фоновые DNS/HTTP задачи. При исчерпании физического лимита монитор остается отзывчивым и показывает ошибку мониторинга. Не прятать это бесконечным перезапуском клиента.
- Shutdown: отменить работу, дождаться ограниченного завершения, убрать иконку и подписки. Не завершать чужие процессы. Не использовать curl/ping.exe/PowerShell в штатном HTTPS-цикле.

## 7. Данные и конкурентность

EndpointDefinition: id, group, uri, infrastructureId. EndpointObservation: endpointId, networkEpoch, attemptId, monotonicStarted/Completed, outcome, httpStatus?, structuredFailure?, elapsed, nextAllowedAt.

EndpointState хранит только последний примененный результат и небольшие счетчики. GroupSnapshot неизменяемый: состояние, reason, время последнего успеха, состояние подтверждения, сведения о точках. Отдельно хранить пригодность пробы и свидетельство связности: 429 дает Reachable в момент ответа, но запрещает следующий запрос до паузы.

Состоянием владеет один последовательный цикл. Рабочие запросы возвращают результаты через ограниченный канал/очередь. UI получает immutable snapshots, а не меняет сетевое состояние. Completion и expiry обрабатываются даже при полном отсутствии сети.

Идентификатор попытки монотонен для точки. Старый completion не отменяет более новый. Результат другого networkEpoch отбрасывается. Сравнение длительностей по TimeProvider.GetTimestamp/монотонному времени; UTC только для отображения/логов/HTTP-date с безопасным переводом в длительность.

Лимиты относятся к инициированным приложением пробам; DNS-повторы ОС и TCP retransmit – не новые application probes. Не обещать пользователю, что запрос равен одному сетевому пакету.

### 8.2 Обычная работа

Round-robin по семи адресам каждой группы. Один адрес примерно раз в 14 с. Не опрашивать весь пул каждые 2 с. Слоты пропущенных/приостановленных точек не догонять пачкой и не передавать оставшимся с повышением их частоты. Никогда две одновременные попытки к одному адресу.

Не вводить автоматическое исключение точки навсегда после сетевых ошибок. При обычном отказе она остается в ротации; один умерший адрес не порождает retry-шторм. Специальная пауза нужна только при явном ограничении/Retry-After, по единому правилу ниже.

### 8.3 Когда нужна дополнительная проверка

Запуск/возобновление/новый networkEpoch: один ограниченный эпизод для получения первого состояния. При обычной работе: неудачи минимум двух разных инфраструктур без Reachable между ними и отсутствие свежего нового Reachable за последние 4 с дают основание начать подтверждение. Одна ошибка при других успешных ответах эпизод не запускает.

Флаг подтверждения отображается текстом в деталях/tooltip. Не мигать красным при первом тайм-ауте. До новых доказательств можно показывать предыдущее состояние только пока его доказательства свежи; по истечении TTL – Unknown.

### 8.4 Как проходит подтверждение

Использовать тот же IProbe и те же глобальные лимиты. Обычные слоты этой группы временно заменяются confirmation-работой, а не идут параллельным потоком. Между двумя группами – справедливое чередование; одна падающая группа не блокирует другую.

EpisodeStart – время старта первой неудачной попытки в последовательности, вызвавшей подтверждение; для старта/новой сети – текущее время. Уже полученные результаты попыток, начатых не раньше EpisodeStart в том же epoch, могут войти в покрытие. Старые положительные результаты не заменяют новую проверку этой точки.

Сформировать набор всех семи настроенных точек. Выбирать непроверенные в эпизоде с наиболее старым lastStarted, соблюдая nextAllowedAt, минимум 8 с и лимиты. Одна новая попытка на точку за эпизод; максимум семь новых вызовов, без рекурсивных retries. Сначала учитывать уже запущенные релевантные запросы, не дублировать их.

- Два новых Reachable от разных инфраструктур: подтверждение доступности закончено. Новые ненужные пробы не запускать. Уже выполняющиеся можно завершить с учетом свежести; если отменяются, Cancelled не считается отказом.
- Весь набор покрыт свежими завершенными результатами: рассчитать состояние по §9.
- Точка в Retry-After, системная ошибка или дедлайн эпизода не позволили завершить покрытие: это не виртуальный отказ. Unknown, если нет достаточных успехов.
- По окончании – обычная ротация без накопленных пропущенных слотов. Во время устойчивого Offline не запускать один эпизод за другим: достаточно обычного опроса для восстановления. Новый успех сразу снимает красный; для зеленого требуется второй независимый успех.

Для восстановления из Offline первый Reachable может запустить тот же ограниченный эпизод, если не нарушен cooldown 15 с; иначе следующий обычный независимый успех даст зеленый. Не вводить специальную ветку по каждому виду транспорта.

### 8.5 Паузы сервера

429: пауза не менее Retry-After, без него 15 минут. 403 без Retry-After: 15 минут. Любой ответ с корректным Retry-After, включая 503: не обращаться раньше указанного срока. Значение в HTTP-date переводить в монотонный deadline; отрицательное/просроченное – минимальная пауза 60 с, некорректное – 15 минут для 403/429/503. Очень большое корректное значение не сокращать: безопасное насыщение внутреннего timestamp, точка явно помечена приостановленной.

В момент такого HTTP-ответа связь подтверждена; после истечения свежести этот адрес дает Unknown, а не воображаемый успех. Пауза не уменьшает quorum и не превращает оставшиеся неответившие точки в полное покрытие. По истечении паузы точка возвращается в обычный слот автоматически.

## 9. Состояния группы и иконки

Ниже только последние, свежие результаты текущего networkEpoch. Положительные голоса считать по infrastructureId, не по числу URL.

| Условие | Состояние |
|---|---|
| Не менее двух независимых Reachable | Online, зеленый |
| Ровно один независимый Reachable | Limited, желтый |
| Нет Reachable; все настроенные точки имеют свежий Unreachable; не менее трех независимых инфраструктур; нет непроверенных/Indeterminate | Offline, красный |
| Иначе | Unknown, серый |

Шесть работают, одна умерла – зеленый. Две работают, пять умерли – зеленый для наличия связности, неисправные адреса видны в деталях. Один работает – желтый, никогда красный. Четыре умерли, три не проверены – Unknown, никогда красный. Все HTTP 429 по проверенному TLS сейчас – наличие связности подтверждено, дальнейшие запросы приостановлены; цвет не удерживается после устаревания данных.

Не смешивать процент доступных сайтов и индикатор наличия связи. UI не должен утверждать «весь интернет исправен». Tooltip: «Провайдер: доступно», «VPN: доступно/ограничено/нет ответа/нет свежих данных». В подробностях объяснить, что проверяется HTTPS контрольных адресов.

Offline на основании полной обычной ротации допустим даже без отдельного эпизода: вся доказательная база свежая. Частичный набор не дает Offline. Отсутствие IP/интерфейса – Unknown с причиной «нет сетевого подключения», без сетевого шторма; событие восстановления запускает получение свежих данных. Локальная ошибка движка – Unknown, не «интернет отключен».

## 10. Быстродействие: цели и обязательные проверки

Нельзя обещать реальные 1–2 с подтверждения полного обрыва. Простая ротация без ускорения имеет верхнюю оценку около 16 с для полного прохода. Дополнительное подтверждение должно улучшать это без ложного красного.

Приемка полного scheduler на виртуальном времени, при 7+7 точках, без серверных пауз, с работающим loop и с отменяемым transport. Для численных границ ниже исходное состояние должно быть установившимся минимум 30 с, без ручных диагностик/событий, расходующих дополнительный бюджет; cooldown завершен. Быстрые границы восстановления 3/5 с относятся к одновременному восстановлению всех семи точек группы. Частичное восстановление рассматривается отдельно. Исчерпанные лимиты, незавершенный cooldown и смена сети проверяются отдельно: лимиты имеют приоритет, состояние не должно сохранять устаревший зеленый, но 14 с в этих условиях не обещаются.

- Healthy → первый отказ отмечен в деталях не позднее 4,25 с после обрыва.
- Healthy → Offline обеих групп при молчании всех точек: не позднее 14 с, для всех фаз смещения момента обрыва относительно расписания. Это требование предстоит доказать, а не уже измеренный факт.
- Одновременный отказ обеих групп не нарушает лимиты и fairness.
- Offline → не красный после первого реального Reachable: доставка в UI не позднее 250 мс после completion; появление самого успешного запроса зависит от текущего слота и сетевой задержки.
- При одновременном восстановлении всех семи точек и ответах за ≤500 мс: восстановление цвета из Offline не позднее 3 с, Online после второго независимого успеха не позднее 5 с в режиме без внешних пауз.
- При восстановлении только одной/двух точек среди остальных неработающих не обещать 3/5 с: следующая живая точка может оказаться в конце ротации. В контрольном режиме обычной ротации, без confirmation, внешних пауз и старых неотменяемых запросов, при ответах живых точек ≤500 мс определить доступность/Online по одной/двум точкам не позднее 15 с. Перебрать все позиции живых точек. Отдельно измерить результат при разрешенном confirmation; он не должен создавать голодание обычной ротации.
- Отдельно измерить worst case при обрыве сразу после успешного confirmation, полном минутном бюджете и активном cooldown. Сохранить максимальную задержку и временные Unknown в документации. Не экстраполировать результат чистого benchmark на эти условия.
- Один навсегда неответивший адрес при остальных здоровых не вызывает Offline, не запускает повторяющийся поток подтверждений, не увеличивает частоту других адресов.
- Если лимиты/Retry-After/OS cancellation не позволяют уложиться в указанные условия, показать Unknown и описать причину, а не фальсифицировать измерения. В тесте без этих исключений превышение – FINDINGS; сначала исправить scheduler, не ослаблять порог молча.

Реальные сетевые интервалы и временные оценки выше не равны SLA интернета. Приемка временных границ приложения проводится с контролируемым транспортом и отдельно со штатным .NET HTTP-клиентом.

## 11. Windows, UI и автономность

- ApplicationContext без главного видимого окна; одно приложение на пользователя/сеанс через именованный mutex. Повторный запуск не создает второй монитор/иконку; существующий экземпляр можно просто оставить работающим.
- NotifyIcon и ContextMenuStrip только на UI thread. Background loop не блокирует message pump. Публикация снимков с объединением обновлений, очередь UI не растет.
- Иконка – круг в нормализованных координатах, радиус с внешним отступом, вырез по вертикали через центр. Левый полукруг провайдер, правый VPN. Прозрачность настоящая alpha, не заливка цветом taskbar. Зазор около 1 px на 16/20 px и 2 px на 24/32 px. Антиалиасинг и проверка при DPI 100/125/150/200%.
- Подготовить ограниченный кэш 16 комбинаций четырех цветов на нужные размеры. Не выделять HICON/Bitmap на каждом тике. Если используется GetHicon, корректно клонировать/освобождать native handle; проверить GDI/USER counts. Dispose при выходе.
- После перезапуска Explorer иконка восстанавливается. Сначала проверить штатное поведение NotifyIcon для TaskbarCreated; добавлять обход только если воспроизводимо нужен. Не держать две иконки и не перезапускать Explorer пользователя ради обычного теста.
- Контекстное меню: «Состояние», «Проверить сейчас», «Диагностика», «Автозапуск», «Выход». Check now использует тот же лимитер/единственный эпизод; многократные клики не умножают запросы. Без навязчивых уведомлений о каждом сбое.
- Компактное окно состояния: две группы, адреса, последнее время/результат, задержка HTTPS, причина отказа, пауза сервера. Не называть длительность HEAD «ping». Показывать время обновления.
- При network change, suspend/resume отменить устаревший epoch, сделать данные Unknown, закрыть старые соединения в ограниченном порядке и получить новые. События debounce, без бесконечного пересоздания HttpClient на шумном событии.
- Смена системных часов не ломает TTL/паузы/частоту. После долгого отсутствия heartbeat UI не сохраняет зеленый: отдельная легкая проверка snapshot age на UI timer, без второго сетевого движка.
- Исключения верхнего уровня наблюдаются, диагностируются; неисправный движок показывает Unknown. Не добавлять цепочку самоперезапуска и watchdog-службу. Fatal internal error не выдавать за сетевой отказ.
- Автозапуск по явному переключателю пользователя, по умолчанию выключен. Реализация HKCU Run с корректным quoting абсолютного пути, без admin. В процессе тестов не включать автозапуск на ПК владельца без его действия; тестировать в изолированном HKCU/VM.

## 12. Настройки, ресурсы, диагностика

Встроенный валидированный пул работает без конфигурирования. Настройки UI в LocalAppData/NetLights, запись атомарная. Не хранить поток результатов постоянно на диск. Для v1 достаточно автозапуска и геометрии окна; редактирование списка адресов – отдельный локальный JSON для продвинутого пользователя с явной валидацией, без UI конструктора правил. При поврежденном пользовательском JSON сохранить его, показать ошибку, использовать встроенный валидный набор с явной пометкой; не менять файл молча.

Валидация: только https, без userinfo/credentials, дубликатов ID, пустых групп, пустых infrastructureId, неожиданных схем. Не считать URL из одного infrastructureId независимыми. Пользовательский набор должен содержать ровно семь адресов в каждой группе, не менее трех infrastructureId на группу, и не может менять константы расписания v1. Иначе отклонить его целиком с понятным сообщением и использовать встроенный набор с явной пометкой. Это сохраняет проверенные границы цикла и возможность подтверждать как Online, так и Offline. Не разрешать конфигурации обходить пределы частоты. Наборы другого размера – отдельное будущее расширение со своими временными тестами.

Лог в памяти: кольцо максимум 2000 записей и 2 МиБ суммарно, обе границы. Не логировать тела, cookies, proxy/VLESS credentials, полные response headers. Предсказуемый структурированный failure code и короткая безопасная диагностическая строка. Export по действию пользователя: snapshot, versions, durations, recent bounded events, config без секретов; ZIP с timestamp. Никакой отправки в сеть. Временная папка удаляется только после успешной проверки архива.

Ручная диагностика по выбранному адресу: повтор HTTPS, при необходимости один ICMP и один TCP/443 к наблюдавшемуся IP. Если IP неизвестен, не угадывать и не сканировать подсети. Все результаты подписаны отдельно. Запросы занимают тот же бюджет; диагностика не меняет цвет напрямую и не обходит Retry-After. При сравнении IP-пробы и запроса по имени явно указывать, что маршруты могут различаться. Не добавлять UDP/QUIC/сканер портов в v1.

Цели ресурсов проверять после прогрева: средний CPU процесса ≤1% одного логического ядра в нормальном режиме; private bytes ≤200 МиБ; после прогрева часовой localhost-прогон без роста private bytes более 20 МиБ и без устойчивого роста GDI/USER/handles. Рабочий набор ОС не использовать единственным критерием утечки. На 24-часовом soak представить график/таблицу по времени; сбор метрик раз в минуту, не гигабайты логов. Если цель не достигнута – измерить источник, не объявлять PASS и не повышать лимит без объяснения.

## 13. Этапы реализации и выходы

1. **Подготовка:** прочитать все ТЗ и фактический git status; сохранить исследования и чужие изменения. Проверить SDK/платформу. Создать solution, проекты, lock-файлы, CI skeleton. Записать архитектуру и константы.
2. **Модель и scheduler без сети:** реализовать фактический core с TimeProvider и fake transport. Сначала полный набор T01–T28 из TEST-MATRIX, включая границы времени, fairness, frozen tasks, 72h virtual. Найти ошибки алгоритма до UI. Выход – trace расписания и доказательства лимитов/латентности.
3. **Реальный HTTPS:** реализовать один .NET клиент. Локальные контролируемые TCP/TLS/HTTP fixtures, без установки trust root. Прогнать T29–T43, отмену и ограничение ресурсов. Протокольная ошибка не заменяется ICMP/TCP.
4. **WinForms:** tray, circle halves, tooltip/menu/details, single instance, network events, export. Прогнать T44–T53. UI должен реально быть видим и управляем, скриншоты и действия обязательны.
5. **Интеграция и длительная устойчивость:** сценарии полной/частичной недоступности, rate-limit, sleep/resume, ротация DNS/соединений, backpressure, T54–T62. Сначала localhost; интернет-тесты только ограниченные и явно отмеченные.
6. **Сборка и handoff:** Release win-x64 self-contained ZIP, без требования установленного runtime; проверить запуск из чистого каталога с пробелами/кириллицей и без admin. Опубликовать только локальные artifacts, без релиза в GitHub или установки на ПК без запроса. Выдать README, acceptance ledger, точные команды, снимки и ограничения.

Минимальная документация по окончании: docs/ARCHITECTURE.md, docs/USER-GUIDE.md, docs/ACCEPTANCE.md, docs/KNOWN-LIMITATIONS.md. Отдельный отчет по тестам со ссылками на raw evidence и git SHA, версиями SDK/runtime/Windows и хешем этого ТЗ.

## 14. Сборка, CI и критерий готовности

CI Windows: restore с lock-файлами, Release build, unit, локальные integration, publish; внешние сайты не должны быть зависимостью CI. Убедиться, что все реально включенные проекты/тесты выполнены, нет тайных skipped/quarantined tests.

Обязательные реальные проверки перед финальным статусом: unit/property/scheduler suite; локальные сетевые fault fixtures; UI lifecycle; 30 минут controlled integration; 60 минут resource soak; 15 минут ограниченного внешнего smoke на финальном .NET клиенте с обычным бюджетом; 24 часа localhost soak готового процесса перед заявлением «готово к автономной эксплуатации». Виртуальные 72 часа не заменяют реальные 24 часа. Частично совпадающие реальные прогоны можно объединить, если один длительный runner собирает все необходимые критерии.

24 часа – фиксированный конечный тест, не постоянная automation. Он не должен опрашивать публичные сервисы: используются локальные управляемые endpoints. Если нет возможности дождаться/выполнить тест, состояние «код готов, автономность NOT RUN», а не PASS. Раздельно: CODE COMPLETE, AUTOMATED VERIFIED, USER-VISIBLE VERIFIED, AUTONOMOUS SOAK VERIFIED, OWNER ACCEPTED. Последнее нельзя назначать вместо пользователя.

Не нужны тесты буквально каждой строки; нужны ветви, которые способны дать ложный цвет, шторм запросов, зависание, утечку или неверное восстановление. Требовать ≥90% branch coverage чистого reducer/scheduler/limiter; исключения перечислить. Coverage не заменяет матрицу и реальные тесты. Изменение дедлайна/таймера/цвета должно ломать соответствующий поведенческий тест.

Не отключать сетевые адаптеры, VPN или интернет владельца для автоматических тестов. Реальный обрыв, отключение VPN, restart Explorer и sleep/resume тестировать в VM/изолированном сеансе либо по отдельному действию пользователя. Отсутствие такого окружения – честный NOT RUN, не повод симулировать скриншоты.
