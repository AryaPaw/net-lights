# Проверка и выпуск Net Lights

Основная реализация находится в `native/` и собирается Rust MSVC. Рабочий процесс локальной проверки, CI и выпуска использует одну точку входа. Не создавайте параллельный пайплайн и не пересобирайте другой кандидат после проверки для упаковки релиза.

## Локальная подготовка без GUI

Для изменения кода или тестового стенда сначала выполните из корня:

```ps1
pwsh -NoProfile -File scripts/verify.ps1 -Preflight
```

Режим проверяет синтаксис поддерживаемых PowerShell-скриптов, самопроверки UI/coverage/лицензий/изоляции, версию, формат, строгий Clippy, тесты рабочего пространства, патча курсора и отдельного frameprobe. Используются закреплённый Rust и существующие каталоги сборки. Режим не устанавливает LLVM coverage tools, не открывает окно, не создаёт Sandbox, не управляет мышью и не меняет рабочий профиль. Он выводит отдельный `PASS` предварительной проверки и `NOT RUN` для остальных уровней; это не готовность выпуска. Первый FAIL останавливает выполнение.

Для быстрой визуальной итерации используйте `cargo build -p netlights-app --locked --target-dir artifacts/rust-target -j 4`. Запускайте этот development-exe только с отдельным `--profile-directory`, скрытым окном и отключёнными обновлениями; снимайте только собственный HWND без активации. Не меняйте ради снимка рабочий профиль или его сохранённый размер. Проверки колеса, наведения и клавиатуры остаются в разрешённом изолированном UI-сценарии, ограничения курсора сохраняются. После завершения серии правок проверяется итоговый Release-кандидат указанной ниже командой.

Для статического осмотра предусмотрен `--inspect-page state|locations|diagnostics|settings|about` вместе с новым изолированным `--profile-directory` и `--skip-automatic-updates`. Окно создаётся скрытым, затем показывается внизу Z-порядка с `SWP_NOACTIVATE`. Флаг несовместим с обычным `--show-local` и `--exit-local`, рабочий профиль запрещён. Дополнительный `--inspect-copy-feedback` доступен только для About: показывает настоящее уведомление успеха, не обращаясь к буферу обмена. Это статический осмотр, не проверка настоящего ввода и не замена hosted UI gate. Завершайте только свой экземпляр через `--exit-local --profile-directory <тот же путь>`.

Локальный патч `gpui-pre` содержит общий движок инерции обычных контейнеров и виртуального списка. Его исходник включён в тестовый harness приложения: проверки `fluent::argus_scroll_patch::engine::tests` запускаются обычными workspace-тестами без окна и GPU. Это проверки математики и состояния, а не измерение плавности настоящего окна. Изменённые файлы патча отдельно проверяются `rustfmt`. Лицензии обоих локальных патчей GPUI должны проходить строгий коллектор перед упаковкой.

## Последовательность CI и разбор падения

1. После локального preflight отправляйте только разрешённый кандидат в разрешённую ветку. При нестабильном UI сначала используйте существующий отдельный `native-ui-diagnostics.yml`, а не параллельный полный CI. Сейчас его guard допускает `codex/1.7.0-ci`; перед запуском сверяйте workflow и разрешённый ref. Например:

   ```ps1
   gh workflow run native-ui-diagnostics.yml --ref codex/1.7.0-ci -f navigation_measurement=false
   ```

   Если меняется сам измеритель движения, включите `navigation_measurement=true`. Автоматически запущенный лишний полный run собственной отладочной ветки можно отменить после сверки его ID и SHA; отмену не считайте успешной проверкой. Main, чужие runs и release workflows не отменяйте ради такой итерации.
2. На FAIL прочитайте traceback, шаг, исходные логи и доступные снимки. Разделите дефект программы, дефект наблюдателя, упаковку и инфраструктуру. Проверьте реальный API установленной зависимости и время измерения. Не объявляйте редкое UIA-наблюдение доказательством пропуска короткого состояния; для изменений доступности используйте события, для плавности – реально представленные кадры и их исходные QPC. Не исправляйте стенд ослаблением predicates, подменой времени или задержкой поведения программы ради теста.
3. Повторите затронутую проверку на исправленном кандидате. Самопроверка стенда должна отвергать соответствующий отказ; mock не подтверждает native доставку событий. После успеха UI запустите полный CI один раз для итоговых входов. Для текущей отладочной ветки ручной запуск без длительного измерения:

   ```ps1
   gh workflow run ci.yml --ref codex/1.7.0-ci -f resource_run=false
   ```

4. Дождитесь результата этого run, проверьте coverage, обязательный motion job и матрицу обновления. При обрыве связи с GitHub сначала перечитайте состояние уже созданного run; не отправляйте повторный dispatch вслепую. Повторять всю сборку после каждого изменения гипотезы не нужно. Новый фикс проверяйте на затронутом уровне, затем возвращайтесь к обязательной полной проверке. Не переиспользуйте бинарник, артефакт или зелёный результат от других входов.

Полный вход, который использует CI:

```ps1
pwsh -NoProfile -File scripts/verify.ps1
```

Команда сохраняет локальные проверки, собирает приложение и агент в новой папке, проверяет настоящие exe в изолированном профиле, затем выполняет функциональный UI и обязательный runtime coverage. Проверяется работа монитора, сигнал готовности после сетевой пробы, две истории, настройки, штатный выход и повторный запуск. Полный режим требует одноразовую hosted CI VM для интерактивной части; локальный запуск без такой среды не может получить итоговый `PASS`. Самопроверка анализатора ресурсов не заменяет измерение программы.

Любой `FAIL` останавливает готовность. Повторный прогон относится только к текущему содержимому исходников. Изменение входных файлов во время проверки блокирует её итоговый `PASS`. Сохраняйте исходные логи и отличайте отказ теста от отсутствия среды.

## Проверка интерфейса и длительной работы

```ps1
pwsh -NoProfile -File scripts/verify.ps1 -NativeUI
pwsh -NoProfile -File scripts/verify.ps1 -ResourceRun
```

Для UI-автоматизации нужен `uv`; версии Python-зависимостей указаны в `scripts/native-ui-smoke.py`. Скрипт работает с собственным HWND через UI Automation и сообщения окна. Полный интерактивный прогон разрешён только на одноразовой GitHub-hosted VM после проверки реальной учётной записи и окружения CI. Локальный запуск через подключённую Windows Sandbox заблокирован до создания VM: RDP синхронизирует курсор, поэтому гостевой токен и nonce не гарантируют отсутствие влияния на мышь пользователя. `SetCursorPos` и `SendInput` в Sandbox запрещены отдельно, повторное наведение при смещении курсора удалено. Это ограничение также блокирует локальную функциональную UI-часть coverage gate; её нельзя отмечать `PASS` или обходить. Проверяются пять страниц на двух языках, восемь периодов, Debug, селекторы, прокрутка, клавиатурная навигация, «О программе», скрытие в трей и физическая геометрия после сброса и перезапуска. Снимки относятся к реальному DPI сеанса. Проверка на одном DPI не подтверждает остальные масштабы.

`-ResourceRun` использует максимальную историю и две настоящие базы. Неполная загрузка баз не считается измерением с базами. Часовой CSV одного процесса проверяется строгим анализатором `test-resource-stability.ps1`; `FAIL` и `INCONCLUSIVE` блокируют готовность. Короткий smoke не называйте проверкой утечек.

Ресурсный job `ci.yml` запускается только через явный `workflow_dispatch` с `resource_run=true`, по умолчанию выключен. Выполняйте его только при действующем запросе длительного измерения; отмена пользователем отзывает этот запуск. Сокращённый прогон можно проводить как отдельную диагностику, но он не проходит часовой gate и не подтверждает отсутствие утечек. Не меняйте пороги ради экономии времени.

Проверяйте установленное обновление настоящими Inno-установщиками. Матрица `scripts/test-ci-upgrade.ps1` запускается только на подтверждённой GitHub-hosted VM. Обязательный `Automatic` проверяет поиск, HTTPS-скачивание, редиректы и оба автоматических перехода 1.6.0 → 1.6.1 → 1.7.0 без ручного вызова агента между ними. Используются неизменённая опубликованная 1.6.0, проверенные установщики и ограниченная HTTPS-лента внутри одноразовой VM. Временное доверие сертификату и переменные прокси очищаются; это не проверка опубликованного публичного канала.

По явному решению пользователя от 2026-11-15 откат исключён из обязательных критериев. `LegacyFailures` остаётся отдельной диагностикой со строгими исходными предикатами и результатами `FAIL` при известных нарушениях старого агента; их нельзя переименовывать в безопасное восстановление. Защита загрузок, проверка версии, работа монитора и сохранность данных остаются обязательными. Реализацию отката из продукта это решение не удаляет.

Для узкой отладки `Automatic` используйте тот же `ci.yml` с `upgrade_payload_run=<ID завершённого полного CI>` и `resource_run=false`. Этот режим допускается только для `codex/1.7.0-ci`, проверяет успешные сборки источника и неизменность продуктовых входов; изменённые тесты выполняются на его настоящих установщиках без повторной полной сборки. Диагностический успех не заменяет итоговый полный CI с пустым `upgrade_payload_run`. Альтернативный `scripts/test-sandbox-update.ps1` предназначен для отдельной собственной Sandbox; не используйте и не закрывайте чужую среду. Его host-режим `-Guest` обязан завершаться до любых изменений. Наличие такого сценария не разрешает управлять локальным курсором.

## Прежняя реализация

C# остаётся в `src/` как источник совместимых контрактов. Для её отдельных unit, integration, smoke и coverage проверок используется `scripts/verify-legacy.ps1` либо `scripts/verify.ps1 -Legacy`. Эти результаты не являются покрытием Rust и не заменяют проверку нативного UI или агента. Не ослабляйте пороги прежних тестов при переносе и не выдавайте пропущенный набор за прошедший.

## Локальный exe

Пользовательская локальная копия находится в `artifacts/publish/NetLights.exe`. После проверки изменений интерфейса, трея или обновления используйте `scripts/run-local.ps1`, затем подтвердите точный путь и ProductVersion процесса. Скрипт завершает только эту копию, ждёт штатного выхода и заменяет файлы транзакционно. Перед переключением реализации сохраните настройки и обе истории; восстановление проверяйте в отдельной папке, не поверх рабочего профиля.

Установленную копию в AppData, релиз и версию не меняйте без отдельного разрешения.

## Версия и публикация

Каноническая версия находится в `Cargo.toml`; совместимая метаинформация `Directory.Build.props` проверяется тем же gate. Номер меняется только по запросу версии или выпуска. Точный номер пользователя повторно согласовывать не нужно; если номера нет, предложите конкретный и дождитесь ответа. Соглашение patch/minor/major определено в корневом `AGENTS.md`.

Коммит, push, тег и публикация требуют соответствующего разрешения по действующему `AGENTS.md`. Перед разрешённой публикацией примените `ap-release-prep` и независимое ревью; перед push – `ap-deploy`. Не переносите существующий тег без отдельного разрешения. Тег `v1.6.1` запускает `.github/workflows/release-bridge.yml`, остальные нативные теги `v*.*.*` – `.github/workflows/release.yml`. Они публикуют GitHub Release, поэтому разрешение должно охватывать этот результат.

`releases/latest` остаётся на 1.6.1: bridge workflow публикует её с `make_latest: true`, нативный workflow использует `make_latest: false`. Это обязательный первый переход для старых клиентов. Bridge и нативные версии читают отдельную стабильную ленту от 1.7.0; не меняйте флаг latest у нативного релиза вручную. Первый переход на bridge по-прежнему выполняется старым агентом: дальнейшая защищённая цепочка не доказывает безопасность отказа самого первого перехода.

Упаковывайте проверенный и просмотренный кандидат. Исправления, генерация и изменения hooks должны войти в окончательные файлы и проверки. После разрешённого push следите только за соответствующими CI runs; локальный `PASS` не доказывает удалённый CI или установленное обновление.

Сохраняйте посторонние staged/unstaged изменения. Не включайте в коммит `TODO.md`, `docs/images/tray-mock.html`, приватные профили, логи, сборки и случайный churn прежних lock-файлов. Не восстанавливайте файлы вслепую после сборки.
